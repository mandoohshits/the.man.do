CASE_01 — THE GHOST IN THE GATEWAY

Networking IP Conflict ARP Managed Switch
01 — THE SYMPTOM

Half the office lost their network randomly. Emails wouldn't sync. Pages wouldn't load. Sessions kept dropping. The key detail — it wasn't completely dead. It was erratic. Working, then not, then working again. That pattern matters.

02 — THE HUNT

First move — continuous ping to the default gateway. Clean for a few rows, then boom. Request timed out. Then a spike to 1500ms. Then back to normal.

ping -t 192.168.1.1

First guess was a failing switch or a network loop. Checked uptime on all switches and access points. Everything looked physically fine. No errors, no resets. Time to go deeper.

03 — THE BREAKTHROUGH

Ran arp -a during one of the drops. The gateway IP was flipping between two completely different MAC addresses every few seconds.

C:\> arp -a
Interface: 192.168.1.50
192.168.1.1  aa-bb-cc-dd-ee-ff  dynamic
← 10 seconds later, same IP, different MAC:
192.168.1.1  11-22-33-44-55-66  dynamic

That's never normal. One IP should only ever belong to one piece of hardware. Two MACs fighting over the same IP meant one thing — IP address conflict.

04 — WHY IT BREAKS EVERYTHING

Every time the rogue device spoke on the network, it told the switches "I own this IP." So did the real router. The switches kept updating their MAC address tables back and forth — creating a tug of war. Every device briefly lost the ability to find the real gateway. That's the erratic pattern everyone experienced.

05 — THE FIX

Used the rogue MAC from the ARP table, logged into the managed switch, found which port that MAC was on, and shut the port down remotely. Network stabilized instantly.

Switch(config)# interface FastEthernet0/[PORT]
Switch(config-if)# shutdown
→ Network stabilized immediately
TAKEAWAY

1. Erratic network = suspect IP conflict before hardware failure.
2. arp -a is one of the fastest diagnostic commands you have — use it early.
3. Never let users manually assign static IPs without checking your DHCP exclusion range first.

CASE_02 — THE PRINTER THAT FORGOT ITS NAME

DHCP Printing Network
01 — THE SYMPTOM

Every time the office printer restarted — power cut, maintenance, firmware update — nobody could print. The printer was on, connected, showing online. But jobs just sat in the queue going nowhere. Classic "it worked yesterday" complaint.

02 — THE CAUSE

The printer was set to DHCP — meaning every time it restarted, it asked the router for an IP address. The router gave it whatever was available. Problem: that IP changed every time. But every computer on the network still had the old IP saved as the printer address. So print jobs were flying off to an IP that no longer belonged to the printer.

Before restart:
Printer IP → 192.168.1.45 ← all computers pointed here

After restart:
Printer IP → 192.168.1.78 ← printer moved, nobody knows
192.168.1.45 → nothing there anymore
03 — THE DIAGNOSIS

First check — ping the printer's saved IP from a computer that can't print:

ping 192.168.1.45
Request timed out.
→ nothing at that IP anymore

Then find where the printer actually went — check the DHCP lease table on the router, or print a network config page directly from the printer's physical buttons. The printer will print its own current IP.

Router DHCP table:
HP-LaserJet-M428  192.168.1.78  aa:bb:cc:dd:ee:ff
← there it is, different IP
04 — THE FIX

Two ways to fix this permanently:

Option A — DHCP Reservation (best way)

Go into the router settings, find the DHCP reservation table, and tell the router "always give this MAC address this IP." The printer keeps using DHCP but always gets the same address.

MAC: aa:bb:cc:dd:ee:ff
Reserved IP: 192.168.1.45
→ printer always gets same IP, forever
Option B — Static IP on the printer itself

Go into the printer's own network settings (usually through its screen menu or web interface) and set a fixed IP manually. Make sure the IP is outside your DHCP range so nothing else accidentally gets the same address.

TAKEAWAY

1. Shared network devices — printers, scanners, servers — should never have a random DHCP address. Always reserve or set static.
2. When a shared device "stops working" after a restart, check its IP first. Nine times out of ten it moved.
3. DHCP reservation is cleaner than static — the device still uses DHCP but always gets the same address. Best of both worlds.
