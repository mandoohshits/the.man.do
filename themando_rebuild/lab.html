CASE_01 — THE GHOST IN THE GATEWAY

Networking IP Conflict ARP
01 — THE SYMPTOM

Half the office lost their network randomly. Emails wouldn't sync. Sessions kept dropping. It wasn't completely dead — it was erratic. That pattern matters.

02 — THE HUNT

Continuous ping to the default gateway. Clean for a few rows, then timeout spikes to 1500ms.

ping -t 192.168.1.1

First guess was a failing switch or loop. Checked everything physically — all fine. Time to go deeper.

03 — THE BREAKTHROUGH
C:\> arp -a
192.168.1.1  aa-bb-cc-dd-ee-ff  dynamic
← 10 seconds later, same IP, different MAC:
192.168.1.1  11-22-33-44-55-66  dynamic

Two MACs fighting over the same IP — IP address conflict. A rogue device had been manually assigned the exact same IP as the gateway router.

04 — THE FIX
Switch(config)# interface FastEthernet0/[PORT]
Switch(config-if)# shutdown
→ Network stabilized immediately
TAKEAWAY

1. Erratic network = suspect IP conflict before hardware failure.
2. arp -a is one of the fastest diagnostic commands — use it early.
3. Never let users manually assign static IPs without checking your DHCP range.

CASE_02 — THE PRINTER THAT FORGOT ITS NAME

DHCP Printing
01 — THE SYMPTOM

Every time the office printer restarted, nobody could print. The printer was on and showing online — but jobs just sat in the queue going nowhere.

02 — THE CAUSE
Before restart:
Printer IP → 192.168.1.45 ← all computers pointed here

After restart:
Printer IP → 192.168.1.78 ← printer moved, nobody knows

Printer was on DHCP — every restart gave it a new IP. But every computer still had the old IP saved. Print jobs flying to an address that no longer existed.

03 — THE FIX
Router DHCP Reservation:
MAC: aa:bb:cc:dd:ee:ff → Always gets 192.168.1.45
→ Printer always gets same IP, forever
TAKEAWAY

1. Shared devices — printers, scanners — should never have random DHCP addresses.
2. When a shared device stops working after restart, check its IP first.
3. DHCP reservation is cleaner than static — same result, less risk.
